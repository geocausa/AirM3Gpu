# AirM3Gpu

Experimental, clean-room bring-up work for the Apple M3 / T8122 G15 GPU on Asahi Linux.

This repository is the **public, reproducible checkpoint** for the work. It intentionally does not contain Apple firmware, kernelcaches, extracted proprietary binaries, Ghidra databases, boot images, built kernel modules, or raw machine-local captures. Those are kept outside this repository; only derived facts, original research notes/scripts, hashes, and source patches are published here.

## Current research state — 2026-08-28

Target hardware: MacBook Air M3 (J615 / T8122), GPU identified at runtime as G15G C0.

The bring-up has advanced well beyond the earlier pre-`MSG_INIT` checkpoint. The isolated candidate now reaches native G15 `MSG_INIT`, post-init bootstrap, persistent RTKit/GpuManager lifetime, DRM registration, and `/dev/dri/renderD128`. Safe host-side GET_PARAMS, VM/GEM lifecycle, unbound VM mappings, passive queue lifecycle, q22 mapping notification, and shared-bank1/range-7 page-table handling are live-tested.

The bounded registration path now reaches and returns from the real G15 scheduler. E056 identified a mis-modeled 0x54-byte DPE leakage-update image at HwDataA `+0x4188`; restoring its exact J615/C0 values removes the earlier cold-power/DPE retrigger loop. E057 then produces scheduler `0x112` snapshots and an accepted `0x111` RunWorkQueue record.

E058-E060 close the remaining registration prerequisites without executing GPU work. A valid stamp number alone is insufficient; a firmware Barrier/type-4 record is required to bind the RunWorkQueue stamp slot to QueueInfo `gpu_buf`. With one already-satisfied Barrier at ring entry 0, the pipe retires to `(Read, CFI, Write, Shadow) = (1,1,1,1)` and callback exit `0x101` appears. E060 also corrects G15 `ReleaseResource` enum numbering to Apple's opcode `0x11`; native teardown then succeeds and firmware returns from software state 1 to state 0 without a crash.

No RunVertex, RunFragment, or RunCompute command and no shader stream is exposed by this proof. E061 now proves that Apple's normal RunCompute/type-3 path is inherently hardware-facing: RTKit copies command `+0x760` into the per-stamp execution record, while Apple's producer always builds a real G15 CDM RegisterArray and SKU stream. There is no justified parser-only RunCompute shortcut. The current boundary is closing the minimum real Compute register/SKU/UMA/completion contract before the first hardware-facing command. E062 closes the SKU packet grammar itself: the no-feature stream is exactly `0x2c0` bytes after alignment, Compute WFI is the single dword `1`, timestamp records are fixed 0x3c-byte opcode-3 packets, and the remaining J615 dynamic register IDs are `0x101d8` and `0x107a0`. E063 additionally proves that RegisterArray `0x1a420` receives the raw CDM control-stream pointer and reconstructs Apple's Gen4 patch/reset framing (`0x60000160` / `0x60000960` plus 16-byte `0x20000000` pointer records). E064 classifies those exact tokens: `0x60000160/0x60000960` are CDM Barriers, `0x20000000` is Stream Link, and Apple G15 emits `0x40000000` as Stream Terminate. The first plausible no-launch payload is therefore a terminate-only CDM root; the unresolved boundary is proving that Apple's normal zero-dispatch Compute container accepts that form with valid surrounding state.

E065-E108 close the next exact-target layers. The stock no-dispatch Compute container was captured and then validated against the matching macOS 14.8.3 / 23J220 G15G driver: the ordinary RegisterArray is exactly 20 entries, the empty descriptor reaches normal `submitBuffer()`, G15 RunCompute `+0x760` is the SKU execution stream rather than the inherited Linux microsequence, and the inactive stock-empty stream is exactly `0x2c0`. E071 corrects the prepared UMA byte at RunCompute `+0x846` to `1`; E072 proves empty-path `+0x847/+0x84f` are zero while `+0x83e` and `+0x857` are live Page-Pool-State/HWMetrics pointers; E073 closes the 64-ID managed context lifecycle and wires the per-ID generation byte to RunCompute `+0x85f`. E074-E076 prove the range-8 parent/leaf ownership and split bank-1 VA allocation without instantiating the FList object. E077 then closes the exact four-resource `AGXUMAFList::init()` contract: 0x70 Page-Pool State in range 8, 8-byte FW-Uncached State in a distinct range-7 class, and exact symbolic Page/Backup List size formulas while deliberately leaving their override-sensitive numeric sizes conditional. E078 models that second range-7 class as leaf `0x00c000000000044b`, adds the exact 8-byte ABI and a hard-wired allocator constructor, while preserving the existing PM/q22 leaf `0x00c0000000000447`. E079 then reconstructs the 0x100-entry HardwareBuffer-ID state machine itself: sticky owner IDs, per-ID references, the zero-reference bitmap, Apple's initial 0→255 allocation order, bitmap fallback/steal behavior, and the 0→1 / 1→0 prepare/complete transitions. E080 wraps that exact state in the driver's established kernel mutex/Arc lifetime and adds an FList-side sticky owner while deliberately creating no runtime instance. E081 then adds a side-effect-free FList resource plan: exact checked symbolic Page/Backup List formulas, compile-time 0x70/8-byte fixed-object sizes, and the synchronized sticky HardwareBuffer owner, but no `GpuObject`, `GpuArray`, allocator handle or command pointer. E082 closes the remaining list mapping class: the exact FList caller option is `0x20000000003` (correcting an older transcription that omitted two zeroes), range-5 outer option `0x20500000007` reduces to compact UAT `0x300`, and Linux gives that cached PTE shape a dedicated FList semantic constant without allocating anything. E083 then proves the J615 override fields remain zero from zero-filled object allocation through configure/start, making the G15G getter defaults exact: M=2 GiB and B=4 MiB. With the exact 16-KiB page, the FList list sizes are 4 MiB / 0x80000 entries and 32 KiB. E084 then cross-checks current public m1n1 AGX structures as a semantic dictionary only: it reinforces Start/Finalize-class SKU, dual-stamp/event-control, page-list/manager, context-vs-VM, multi-counter/timestamp, and queue-state concepts without importing any old offset or opcode. E085 closes the q22 prerequisite for the future range-8 Page-Pool-State mapping: ordinary range 7 remains map/unmap `1/0`, while Apple's special 64-MiB range 8 uses exact `3/2`. E086 then adds the four-object FList persistent backing owner as unreachable compile-only code, stopping at the exact constructor seed and exposing no Page-Pool-State command pointer. E087 closes the lower-level residency lifetime: first HardwareBuffer activation prepares/commits the mappings, later complete drops preparation references without releasing PTEs, and PTE teardown is a separate FList lifetime. E088 then closes the normal success-path stamp/retirement chain and proves RunCompute `+0x14` is the rotating command-buffer event-control FWVA, distinct from the generic descriptor submit event that gates WorkQueue pruning. E089 removes the inherited wrong-lifetime queue-wide notifier from that G15 field and leaves the event-control FWVA zero/fail-closed until the exact 36-state owner exists. E090 closes the recovery side: destructive restart force-completes stamps into the ordinary scheduler/prune/descriptor-complete path, then separately drains cached context state, pending UMA grow/request references, sticky FList HardwareBuffer ownership, page-pool state and channel state; preserve/restart states remain distinct and are not given guessed enum names. E091 then models the exact rotating event-control ownership geometry—36 opaque 0xc0-byte states, contiguous 0x1b00 total, increment-before-select modulo 36—without implementing `GpuStruct`, choosing a mapping class, allocating GPU memory or publishing RunCompute `+0x14`. E092 closes that mapping ambiguity on exact 23J220: the command buffer uses one contiguous 0x90-byte stamp backing in normal range 7 (`0x700000007`, leaf `0x...0447`) and one contiguous 0x1b00-byte event-control backing in range 8 (`0x20800000007`, leaf `0x...0443`); construction zeroes the pools and links each control `+0x00` to its matching stamp FWVA, while the rotation-time `+0x10` config value remains deliberately unresolved. E093 promotes only that proven construction boundary into unreachable compile-only ownership: exact-base shared-data allocations for the two pools, q22 ownership, and per-control `+0x00` stamp linkage are modeled, but the owner has zero call sites and RunCompute `+0x14` remains zero. E094 closes the selected-state numeric seed on normal J615: accelerator `+0x2428` remains zero, so event-control `+0x10` is exactly the 80-record G15 fallback; Linux can reproduce the post-finish reset/seed image while deliberately exposing no selected FWVA. E095 then proves slot rotation is guarded by host-event retirement and corrects event-control `+0x08` to the unmasked shared state sequence, not a stamp index. E096 models that reuse barrier with the existing Linux per-submission `JobFence`: occupied/in-flight slots remain unavailable until their pending command count reaches zero. E097 then closes the separate HWMetrics pointer producer: exact 23J220 owns one zeroed 0x4000-byte range-7 page, advances 0x40-byte records modulo that page, maps it with option `0x0001008700000007`, reduces to compact UAT `0x30b`, and emits exact bank-1 leaf `0x00e000000000040b`, bit-identical to Linux `PROT_GPU_FW_SHARED_RW`. E098 adds only an unreachable page-base HWMetrics owner and hard semantic aperture/protection pairing; RunCompute `+0x857` remains zero. E099 then models the exact post-`populatePagePool()` FList firmware-state image behind the first HardwareBuffer epoch, validating dynamic page/list counts and publishing only owned Page/Backup/FW-Uncached FWVAs into the unreachable 0x70 state. E100 closes the stock-empty first-activation contents specifically: the exact type-5 UMA accounting oracle stays zero around a successful empty Compute command, proving no nonzero pool-growth path; the Page/Backup lists therefore remain zero-filled, page count/cursors and Backup extent count are zero, while mapped resources, capacity `0x80000`, and the real HardwareBuffer ID remain real. Linux models that exact empty image in an unreachable helper and still exposes no `+0x83e` pointer. E101 then re-audits the exact 23J220 inactive stock-empty SKU payload source-by-source, correcting the setup-payload `+0x3c/+0x40` split and timestamp UUID field while closing the type-0xc backpointer/bookkeeping and J615 channel-region geometry. E102 implements that map as an unreachable byte-exact `0x2c0` serializer whose inputs are all runtime-owned addresses/state; it owns no GPU memory, has zero call sites, and does not change RunCompute `+0x760`. E103 then closes the encoder backing itself: normal J615 has exactly `0xf0` SKU slots at `0x300` bytes, one page-rounded `0x30000` special-range-8 backing, and a separate `0x3c00` host event array; the range-8 mapping is the already-live-proven `0x...0443` class and is retained for encoder lifetime. E104 models only that GPU backing as an unreachable zero-filled page-base owner with no selected-slot/FWVA accessor and no link to the E102 serializer. E105 then closes exact SKU slot reuse: Apple scans from the next slot modulo `0xf0`, requires the per-slot command event to test complete, copies the new command event into the selected host guard, and returns GPU-base + `slot*0x300` from `finishEncode()` as RunCompute `+0x760`. E106 models that reuse rule conservatively with the existing whole-submission `JobFence`: it can delay reuse but cannot permit premature overwrite, and remains definition-only. E107 adds that copy boundary without publishing it: after an E106-retired slot is supplied, Linux clears the complete `0x300` slot, copies exactly the E102 `0x2c0` stream, preserves the final `0x40` zero slack, and returns only a definition-only prepared token with slot/FWVA/size. E108 then groups the exact event-control, HWMetrics, FList/HardwareBuffer and SKU backing owners under one unreachable construction graph sharing the same bank-1/q22 lifetime while preserving their distinct activation/retirement epochs. The graph exposes no FWVA, selects no slot and has zero call sites. The current clean Linux checkpoint is `ea707e8e7726`, published as patch `0031`. Live RunCompute remains fail-closed until a separate unpublished per-command assets token can bind already-retired event/SKU slots to already-prepared FList/HWMetrics state without creating any RunCompute consumer.

## Status

This is bring-up/research code, not a production driver. Every live gate is intentionally staged and fail-closed. Do not treat the patchset as general M3 GPU enablement yet.
